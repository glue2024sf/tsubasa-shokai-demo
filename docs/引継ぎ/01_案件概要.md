## 2. プロジェクトのゴール

クライアントの根源的な動機は **「事務コン（基幹の販売管理ソフト）を2026/09末で解約する」** こと。その期限までにSalesforceへ業務を載せ替える。

| # | ゴール | 背景・狙い |
| --- | --- | --- |
| G1 | **事務コンからの脱却** | 既存システムが2026/09/30で解約。それまでに受注〜請求の業務をSFへ移行する（=本案件の最終納期を規定する制約） |
| G2 | **売上・入金の可視化** | 経営層（山口様）が数字をリアルタイムに把握できる。特に未入金の可視化 |
| G3 | **見積／請求書発行の一元化** | 事務コンに依存していた帳票発行をSF内でボタン1つで完結。属人化の解消 |

## 3. 解決したい課題（As-Is の痛み）

ヒアリング（項目No.9）で明確になった現状の課題：

- **過去データの呼び出しが遅い** ― 事務コンで前回の受注金額・単価を確認するのに時間がかかる。
- **業務が事務員1名に属人化** ― 山口様（経営層）は事務コンの操作を把握しておらず、**事務員が休むと受注・請求が止まる**。
- **数字が見えない** ― 売上・入金状況がリアルタイムに把握できない。未入金の取りこぼしリスク。

### As-Is 業務フロー
```
問い合わせ（FAX-DM／Meta広告）
  → 事務員が事務コンに受注入力
  → 見積書を確認・顧客情報入力・伝票発行
  → 受注 → 商品出荷
  → 請求書発行（事務員・事務コン）
  → 事務員がネットバンキングで入金確認（日次）
```

### To-Be 業務フロー（Salesforce）
```
リード／取引先（サンプル送付管理）
  → 商談作成 → 明細入力 →［見積書PDF生成ボタン］
  → フェーズ更新（受注=100%）→ 請求書レコード自動生成（Flow）
  → 出荷情報入力（出荷日／運送会社／追跡番号）→［請求書PDF生成ボタン］
  → 入金確認（事務員）→ 入金日入力
  → ダッシュボードで未入金アラート（60日超=赤）
```

## 4. ビジネスモデル・取引の特徴（構築上の前提）

| 観点 | 内容 | 設計への影響 |
| --- | --- | --- |
| 顧客チャネル | **新規が99%**。FAX-DM・Meta広告から流入 | リード→取引先変換フロー、流入経路の管理 |
| 取引頻度 | 受注 **1〜3件/日**、平均単価 **¥150,000** | 大量データではないが日次運用に耐える設計 |
| 営業手法 | **サンプル送付**が肝。送付済かどうかの管理が重要 | リード・取引先**両方**にサンプル送付チェック＋送付日。重複送付防止 |
| 配送 | 1取引先に**最大3つの配送先住所**（圃場・倉庫など） | 取引先に配送先×3、商談で配送先を選択 |
| 入金管理 | ネットバンキングで日次確認。未入金が経営リスク | **発行60日超で未入金アラート（赤表示）**、過去未入金の積み上げ可視化 |
| 会計期 | **2月〜1月**（一般的な4月始まりではない） | SFをカスタム会計年度（2月開始）に設定。当期集計の期間定義に影響 |
| 税 | **外税10%**・プラ製品のみ（軽減税率対象なし） | 帳票に外税10%の税額行が必要 |
| 振込先 | **2口座を常時併記**。自社で口座を追加・変更したい | 振込先口座マスタ＋自社編集UI、請求書に常時2口座表示 |
| 会計連携 | **不要**（SF内で請求書発行まで完結） | MoneyForward API連携はアウトオブスコープ |

## 5. スコープ

### MVP（本番リリース対象）
M1 取引先・リード管理（サンプル送付・配送先×3）／M2 商談管理（明細・自動採番・出荷・入金）／M3 見積書PDF／M4 請求書自動生成／M5 入金管理（未入金日数・60日アラート）／M6 振込先口座マスタ／M7 サンプル送付集計／M8 ダッシュボード（経営・営業・事務）／M9 データ移行

### 当初Phase2 → 5/22要件で前倒し済み
- 納品書・出荷指示書PDF（**デモには実装済み**。受注時に請求書とあわせ3帳票自動生成）

### アウトオブスコープ（明示）
- MoneyForward等の会計ソフトAPI連携
- 取引先責任者（Contact）管理 ※法人単位のみで運用
- メール／LINE等の双方向連携・在庫管理
- 領収書PDF・弥生会計CSV連携（必要が出れば追加見積）
